# RosSimulator 测试用例文档

| 项目 | 内容 |
|------|------|
| 测试对象 | RosSimulator（C++ 模拟 ROS 发布订阅系统） |
| 测试环境 | Windows / Visual Studio 2022 / Debug x64 |
| 测试方法 | 运行 `main` 演示程序，核对控制台输出与 `run.log` 落盘内容；异常场景由 main 内置的异常演示段触发 |
| 测试日期 | 2026-11-18 |

## 一、测试范围说明

- **正常场景**：多发布者、多订阅者的注册、发布、接收全链路
- **边界场景**：同一话题多订阅者、时间戳一致性
- **异常场景**：空节点名、空消息内容、重复注册、向无订阅者话题发布

## 二、正常场景用例

### TC-01 订阅者注册

| 项 | 内容 |
|----|------|
| 步骤 | 程序启动，3 个订阅者依次调用 `Init()` |
| 预期 | 每个订阅者打印一条 `[INFO] 订阅了` 日志 |
| 实际 | `温度显示器A 订阅了 sensor/temperature` 等 3 条全部出现 |
| 结论 | ✅ 通过 |

### TC-02 发布者注册

| 项 | 内容 |
|----|------|
| 步骤 | 3 个发布者依次调用 `Init()` |
| 预期 | 每个发布者打印一条 `[INFO] 发布话题` 日志 |
| 实际 | 3 条日志全部出现 |
| 结论 | ✅ 通过 |

### TC-03 一发多收（核心特性）

| 项 | 内容 |
|----|------|
| 步骤 | 温度传感器发布 `21.1 C`（订阅者：显示器A + 记录器B） |
| 预期 | 两个订阅者**都**收到同一条消息，各打印接收日志与业务日志 |
| 实际 | `[温度显示器A 收到: 21.1 C]` 与 `[温度记录器B 收到: 21.1 C]` 相继出现 |
| 结论 | ✅ 通过 |

### TC-04 话题隔离

| 项 | 内容 |
|----|------|
| 步骤 | 温度话题发布后，紧接着湿度话题发布 `41 %` |
| 预期 | 温度消息只到达温度订阅者，湿度消息只到达湿度显示器，互不串扰 |
| 实际 | 与预期一致，无任何交叉 |
| 结论 | ✅ 通过 |

### TC-05 自定义消息类型（加分项 10.3）

| 项 | 内容 |
|----|------|
| 步骤 | 发布 `TemperatureMessage(21.1, "C")`，显示器A 回调用 `dynamic_cast` 取结构化数据 |
| 预期 | 回调从 `GetValue()/GetUnit()` 取值并输出，且能执行业务判断（>25 报高温） |
| 实际 | 输出 `显示器A 处理: 21.1 C (正常)`，转换成功 |
| 结论 | ✅ 通过 |

### TC-06 日志持久化（加分项 10.2）

| 项 | 内容 |
|----|------|
| 步骤 | 运行结束后打开 `run.log`，再运行一次，再次打开 |
| 预期 | 控制台与文件内容一致；第二次运行的内容**追加**在文件末尾 |
| 实际 | `run.log` 累计 30+ 行，多次运行记录依次累加，与 `docs/example_output.log` 对应 |
| 结论 | ✅ 通过 |

## 三、边界场景用例

### TC-07 多订阅者挂同一话题

| 项 | 内容 |
|----|------|
| 步骤 | 两个订阅者注册同一话题 `sensor/temperature`，发布 3 条 |
| 预期 | 每条消息都被两个订阅者各自收到，共 6 条接收日志 |
| 实际 | 6 条全部出现，顺序与注册顺序一致 |
| 结论 | ✅ 通过 |

### TC-08 时间戳一致性

| 项 | 内容 |
|----|------|
| 步骤 | 观察同一时刻发布的一条消息在两个订阅者日志中的时间戳 |
| 预期 | 完全相同（同一份 Message 对象，时间戳在发布端生成） |
| 实际 | 两个订阅者显示的时间戳一致 |
| 结论 | ✅ 通过 |

## 四、异常场景用例

### TC-09 空节点名

| 项 | 内容 |
|----|------|
| 步骤 | 尝试创建 `Publisher("", "sensor/x")` |
| 预期 | 抛出 `NodeException`，被 main 捕获，打印提示，程序继续 |
| 实际 | `[ERROR] 已拦截 -> 节点名不能为空` |
| 结论 | ✅ 通过 |

### TC-10 空消息内容

| 项 | 内容 |
|----|------|
| 步骤 | 调用 `Publish("")`，触发 `Message("")` 构造 |
| 预期 | 抛出 `MessageException`，被捕获，程序继续 |
| 实际 | `[ERROR] 已拦截 -> 消息内容不能为空` |
| 结论 | ✅ 通过 |

### TC-11 重复注册

| 项 | 内容 |
|----|------|
| 步骤 | 已注册的 `温度传感器` 再次调用 `Init()` |
| 预期 | 抛出 `NodeException`，被捕获，程序继续 |
| 实际 | `[ERROR] 已拦截 -> 同一发布者不能重复注册同一话题` |
| 结论 | ✅ 通过 |

### TC-12 向无订阅者话题发布

| 项 | 内容 |
|----|------|
| 步骤 | `气压传感器` 向 `sensor/pressure` 发布（无人订阅） |
| 预期 | 记 WARN 日志，**不抛异常**，后续发布不受影响 |
| 实际 | `[WARN ] 话题 sensor/pressure 暂无订阅者，消息丢弃: 1013 hPa`，之后流程正常 |
| 结论 | ✅ 通过（设计原则：运行时状态记日志，不抛异常） |

## 五、测试结论

| 类别 | 用例数 | 通过 | 失败 |
|------|--------|------|------|
| 正常场景 | 6 | 6 | 0 |
| 边界场景 | 2 | 2 | 0 |
| 异常场景 | 4 | 4 | 0 |
| **合计** | **12** | **12** | **0** |

全部 12 条用例通过。系统在正常输入下功能正确，在非法输入下**抛出语义清晰的异常且不崩溃**，生命周期（注册 → 收发 → 关闭 → 清表）完整可控。运行证据见 `docs/example_output.log`。
